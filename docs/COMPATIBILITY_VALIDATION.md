# Compatibility validation

This report records local validation of the unreleased `0.3.0.dev0` revision on 2026-10-20. It distinguishes executed checks from configured CI. Passing these checks does not establish every optimizer/device combination or guarantee training quality on other workloads.

## Method

The host is macOS 26.6.2 on Apple arm64 with 16 GB memory. Temporary environments and source snapshots were placed outside the iCloud-managed checkout to avoid file offloading. One reusable compatibility environment was used sequentially; numerical-library thread limits were set to one per process, including two-rank Gloo tests. The single-process training-mode fixture permits at most two PyTorch threads. One primary-suite run briefly overlapped a compatibility run; these are per-run limits, and elapsed times are descriptive rather than controlled performance comparisons. The shared host also entered system sleep during this session. Recorded timers may exclude suspended time and must not be interpreted as uninterrupted wall-clock durations; this timing limitation does not change the recorded correctness outcomes. The evidence records interpreter, PyTorch, NumPy, pytest, source-file hashes, test results, skips, and both pip and uv dependency checks.

The expanded suite includes independent scheduler calculations and invalid-input checks, checkpoint restoration, tensor learning rates, training contracts, real optimizer steps, CPU/Gloo distributed recovery, supported mixed-precision/compiled-model modes, MPS checks where available, and workload-protocol validation. Optional Lightning tests are intentionally separate from the core environment. See [distributed validation](DISTRIBUTED_VALIDATION.md) and [training-mode validation](TRAINING_MODES_VALIDATION.md) for their precise limits.

## Findings during compatibility execution

The actual Python 3.8 run exposed use of `math.ulp` in regression tests, which Python 3.8 does not provide. Those test constants now use exact binary64 `float.fromhex` values; the runtime scheduler did not require a corresponding change. Subsequent Python 3.8 testing passed the then-current 263-test suite, including a separate installed-wheel run outside the checkout. A later regression verifies that checkpoint restoration retains tensor-valued `base_lrs`. The expanded floor run then exposed a genuine older-PyTorch defect: PyTorch 2.0 initially aliases tensor-valued `initial_lr` and `base_lrs` to the live learning-rate tensor. In-place updates consequently changed supposed base metadata, and checkpoint continuation differed from uninterrupted execution. DLRS now isolates tensor initial/base metadata during construction and restoration. Regression tests cover ownership, legacy alias restoration, and continued updates; all final matrix cells use this corrected implementation.

Native probes without DLRS reproduced additional PyTorch limitations on this host. On PyTorch 2.0.0, compiling a model could stop optimizer post-step hooks firing despite real parameter updates; the test helper now counts explicit successful `optimizer.step()` calls for ordinary steps and retains hooks only for detecting GradScaler-skipped steps. Native MPS random/dropout sequences failed exact replay after restoring device RNG state on both PyTorch 2.0.0 and 2.4.1. The stochastic-MPS restart tests now independently check native replay before constructing a DLRS scheduler. If replay fails, those two tests record the failed native capability and skip; unexpected errors still fail. These skips are unverified stochastic-MPS recovery, not successful restart results. The native reproduction and measurements are retained in [the probe](../benchmarks/native_training_mode_probe.py), [2.0.0 evidence](native-training-mode-torch200.json), and [2.4.1 evidence](native-training-mode-torch241.json).

The upstream macOS arm64 PyTorch 2.0.0 wheel has an inconsistent internal wheel tag: its downloaded filename identifies arm64, but its `WHEEL` metadata declares `cp38-cp38-macosx_11_0_x86_64`. The installed `libtorch_cpu.dylib` is an arm64 binary and the tests execute, but both pip and uv dependency checks report the incompatible internal tag. This validation does not modify third-party metadata or treat that dependency check as passing. This observation is specific to the inspected macOS/Python 3.8 wheel; it is not evidence of an issue with the Linux CI wheel.

## Distribution and CI checks

The source distribution includes tests, examples, benchmark code and its JSON protocol, documentation/evidence, and the distribution-validation helper. The helper installs the wheel and source archive independently into a non-editable environment, checks dependencies and metadata, removes the extracted source package, and runs the extracted tests against the installed artifact. This prevents a checkout import from concealing a broken distribution. It also records artifact SHA-256 hashes before execution, installed dependency versions, test logs, and partial output on timeout. Exact final archive identities and outcomes are emitted to a separate output directory; they cannot be embedded in the source archive without changing that archive's own hash. CI retains this output as the `distribution-validation` artifact. Local final-build output is retained separately under `.audit/distribution-validation/`.

The CI workflow now runs that same installed-artifact validation and retains each test cell's JUnit outcomes, including native-capability observations. Its dedicated Lightning job requires the tested framework versions and exercises both fresh-process checkpoint continuation and early rejection of unsupported accumulation, precision, and competing-scheduler configurations. CI version selections are documented in [CONTRIBUTING.md](../CONTRIBUTING.md). At the close of the 2026-10-20 local validation, this revision had not been pushed or executed by GitHub Actions. The results above remain that dated local evidence; consult [GitHub Actions](https://github.com/Thabhelo/pytorch-dlrs/actions) for subsequent remote runs. Workflow configuration alone is not a completed run.

## Remaining boundaries

No Linux or Windows runtime was available for this local run. Docker was installed but its daemon was not running; it was not started. Linux and Windows jobs remain configured, unexecuted validation. CUDA, ROCm, NCCL, multi-node behavior, CUDA graphs, compiler-captured scheduler updates, FSDP/ZeRO, and production-scale recovery remain outside these measurements. MPS and CPU/Gloo checks are limited to their recorded tests and do not imply coverage of those other stacks.

The package runtime depends only on PyTorch. NumPy is needed by tests and examples; test/development extras use NumPy 1.x below Python 3.13 for old-PyTorch compatibility and NumPy 2.x on Python 3.13+. The Python 3.14/NumPy 2 test-extra installation was executed and passed dependency checks; Python 3.13 itself was not run. Test-environment dependency choices do not expand the scheduler's runtime dependency set. Core numerical correctness and packaging checks cannot establish that DLRS improves another user's model; compare fixed-budget, multiple-seed workload results separately.
